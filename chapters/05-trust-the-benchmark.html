Chapter 05Chapter outlineLab planned

Can you trust your benchmark?

We’ll look at the program that sends requests and records their times. Its own limits can make a database appear slower or hide work that is waiting. You’ll learn to check the measuring process before using its numbers to compare systems.

This is a chapter outline. The worked example and executable lab are planned. You can use the design task below to start your benchmark brief.

What you will learn

  • Define what belongs inside the timed interval.
  • Distinguish work submitted, work completed and work still waiting.
  • Recognise when the request-sending program limits the test or omits waiting time.

01 / The question

Start with a customer decision

So far, we’ve focused on the systems and the work we ask them to do. Now we’ll examine the benchmark runner: the program that prepares the test, sends requests and collects results. It is part of the experiment and can affect what we observe.

Imagine that completed requests stop increasing as we ask for more work. The database might be at its limit, or the runner might be unable to send requests quickly enough. A runner that waits for every response before sending the next request also changes the demand when responses slow down.

We’ll inspect where the clock starts and stops, count work sent and completed, and investigate the runner’s limits. These checks help establish whether a measured difference belongs to the systems being compared or to the way we tested them.

02 / Worked example · planned

The comparison to build

Inspect a supplied runner that includes input generation in one timing and excludes it in another. Then investigate a client that waits for a response before submitting more work.

03 / Experiment · planned

How the lab will work

  1. Separate startup, setup, warm-up and measured operation.
  2. Record intended arrivals, actual submission, completion, errors and timeouts.
  3. Change client capacity or pacing and examine achieved work and outstanding requests.

The executable lab, reference outputs and progressive hints will be added when this chapter is implemented.

04 / Design task

Start your benchmark brief

Define the timing boundary and arrival model for your comparison. Add a control experiment that could reveal a client-side limit.

05 / Keep the evidence

What your record should contain

  • Runner version, commands and timing boundaries
  • Offered and achieved rates, errors and pending work
  • Client-resource observations and the control run

06 / Interpret

What the evidence can support

A timed batch average is not an individual-request latency distribution. Document warm-up and background work; a stable-looking chart alone does not establish steady state.
