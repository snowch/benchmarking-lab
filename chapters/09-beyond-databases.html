Beyond databases

We’ll apply the comparison method to Kafka, which carries streams of events between applications. We’ll also consider object storage and search. You’ll learn which checks carry over from databases and which definitions of success must change for a different technology.

This is a chapter outline. The worked example and executable lab are planned. You can use the design task below to start your benchmark brief.

What you will learn

  • Define completion and service guarantees for a new technology.
  • Design a Kafka test that tracks events delivered and work waiting to be read.
  • Adapt the benchmark brief to object storage or search.

01 / The question

Start with a customer decision

The earlier chapters gave us a way to define useful work, check answers and measure performance. Those habits also apply outside databases, but the work and the point at which we call it complete can change.

Kafka stores streams of events, such as new orders, so applications can read and process them. A sending application is a producer; a reading application is a consumer. A broker is a server that stores and serves those events.

Imagine a customer who needs each new order to reach a fulfilment application within a target time. Kafka accepting an event and the application processing it are different milestones. We’ll use this distinction to design a comparison, then consider how success changes again for storing files or returning useful search results.

02 / Worked example · planned

The comparison to build

Design a Kafka experiment that distinguishes producer acknowledgement, consumer receipt and downstream processing. Document message sizes, batching, compression, partitions, replication and acknowledgement semantics.

03 / Experiment · planned

How the lab will work

  1. Use a real broker and record client, server and workload configuration.
  2. Increase offered rate while measuring delivered work, latency, errors and lag.
  3. Pause a consumer, resume it under continuing arrivals and inspect catch-up and event identities.

The executable lab, reference outputs and progressive hints will be added when this chapter is implemented.

04 / Design task

Start your benchmark brief

Write a benchmark brief for object storage or search. Define correctness, completion and guarantees before choosing a tool.

05 / Keep the evidence

What your record should contain

  • Kafka workload, topology and service-guarantee records
  • Correlated event observations and consumer-lag history
  • Loss, duplication and ordering checks with their limits

06 / Interpret

What the evidence can support

Browser diagrams will explain the workflow; a downloadable harness will run against real services. Object size and request costs matter for storage; relevance and indexing delay matter for search.
